# Python 3.14 Support: Implementation Plan

Unblock Python 3.14 users by making ChromaDB/ONNX optional and adding a
lightweight SQLite FTS5 fallback for vector search.

---

## Problem Statement

- ChromaDB depends on `onnxruntime`, which does not ship Python 3.14 wheels.
- `model/vector_db.py` imports `chromadb` **at module level** — the app
  crashes on import on 3.14.
- `controller/commands.py` calls `onnx_manager.download_model_if_needed()`
  **unconditionally** during startup.
- `pyproject.toml` lists `chromadb` in `install_requires` — pip resolution
  fails on 3.14 before the app is even installed.

Result: Aye Chat cannot be installed or run on Python 3.14 at all.

---

## Design Goals

1. **3.10–3.13**: Zero behaviour change. ChromaDB + ONNX continues to work
   exactly as today.
2. **3.14+**: App installs and runs. RAG uses SQLite FTS5 (lexical search)
   instead of semantic embeddings. Quality is lower but functional.
3. **Minimal code churn**: No large refactor. Introduce a thin facade over
   the two backends and gate imports.
4. **No new heavyweight dependencies**: FTS5 uses `sqlite3` (stdlib).

## Implementation Steps

### Step 1 — Detect backend availability at runtime

**New file:** `model/vector_backend.py`

This is the single source of truth for which backend is active.

```python
"""Vector search backend detection and selection."""

import sys

_backend: str | None = None


def _detect_backend() -> str:
    """Detect which vector search backend is available.

    Returns 'chroma' if chromadb can be imported, 'fts' otherwise.
    """
    try:
        import chromadb  # noqa: F401
        return "chroma"
    except ImportError:
        return "fts"


def get_backend() -> str:
    """Return the active backend name: 'chroma' or 'fts'."""
    global _backend
    if _backend is None:
        _backend = _detect_backend()
    return _backend


def is_chroma_available() -> bool:
    return get_backend() == "chroma"


def is_fts_backend() -> bool:
    return get_backend() == "fts"
```

No chromadb import at module level — only inside the `try` block.

**Risk:** Low. New file, no callers yet.

### Step 2 — Create the SQLite FTS5 backend

**New file:** `model/vector_db_fts.py`

This module mirrors the public API of `vector_db.py` but uses SQLite FTS5
for lexical (BM25) search instead of vector embeddings.

#### Schema

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS chunks USING fts5(
    id UNINDEXED,
    file_path UNINDEXED,
    content,
    tokenize = 'porter unicode61'
);
```

- `id`: chunk identifier (e.g. `"src/foo.py:3"`).
- `file_path`: stored but not indexed (used for filtering/delete).
- `content`: the chunk text — this is what FTS indexes.
- `tokenize`: Porter stemmer + unicode61 tokenizer. Good for code
  identifiers and English comments.

#### Public functions

Match the same signatures as `vector_db.py` so callers don't need to
know which backend they're using:

```python
def initialize_index(root_path: Path) -> Any:
    """Open (or create) the FTS database.

    Returns an opaque connection wrapper that the other functions accept
    in place of a ChromaDB collection.
    """
    db_path = root_path / ".aye" / "fts_index.db"
    db_path.parent.mkdir(parents=True, exist_ok=True)
    conn = sqlite3.connect(str(db_path), check_same_thread=False)
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("""
        CREATE VIRTUAL TABLE IF NOT EXISTS chunks USING fts5(
            id UNINDEXED,
            file_path UNINDEXED,
            content,
            tokenize = 'porter unicode61'
        )
    """)
    conn.commit()
    return conn


def update_index_coarse(conn: Any, files_to_update: Dict[str, str]) -> None:
    """Insert/replace coarse (whole-file) chunks."""
    for file_path, content in files_to_update.items():
        # Delete existing chunks for this file first
        conn.execute("DELETE FROM chunks WHERE file_path = ?", (file_path,))
        conn.execute(
            "INSERT INTO chunks (id, file_path, content) VALUES (?, ?, ?)",
            (file_path, file_path, content),
        )
    conn.commit()


def refine_file_in_index(conn: Any, file_path: str, content: str) -> None:
    """Replace coarse chunk with fine-grained AST chunks."""
    conn.execute("DELETE FROM chunks WHERE file_path = ?", (file_path,))

    language_name = get_language_from_file_path(file_path)
    chunks = []
    if language_name:
        chunks = ast_chunker(content, language_name)
    if not chunks:
        chunks = _chunk_file(content)
    if not chunks:
        return

    rows = [
        (f"{file_path}:{i}", file_path, chunk)
        for i, chunk in enumerate(chunks)
    ]
    conn.executemany(
        "INSERT INTO chunks (id, file_path, content) VALUES (?, ?, ?)",
        rows,
    )
    conn.commit()


def delete_from_index(conn: Any, deleted_files: List[str]) -> None:
    """Delete all chunks for the given file paths."""
    if not deleted_files:
        return
    placeholders = ",".join("?" for _ in deleted_files)
    conn.execute(
        f"DELETE FROM chunks WHERE file_path IN ({placeholders})",
        deleted_files,
    )
    conn.commit()


def query_index(
    conn: Any,
    query_text: str,
    n_results: int = 10,
    min_relevance: float = 0.0,
) -> List[VectorIndexResult]:
    """BM25 full-text search over indexed chunks."""
    if not query_text:
        return []

    # Sanitize: FTS5 query syntax uses double quotes for phrases.
    # Wrap each token in quotes to avoid syntax errors from special chars.
    tokens = query_text.split()
    fts_query = " OR ".join(f'"{t}"' for t in tokens if t.strip())
    if not fts_query:
        return []

    rows = conn.execute(
        """
        SELECT id, file_path, content, rank
        FROM chunks
        WHERE chunks MATCH ?
        ORDER BY rank
        LIMIT ?
        """,
        (fts_query, n_results),
    ).fetchall()

    results = []
    for row_id, file_path, content, rank in rows:
        # FTS5 rank is negative (more negative = more relevant).
        # Normalize to a 0–1 score. -20 is a rough floor.
        score = max(0.0, min(1.0, 1.0 + rank / 20.0))
        if min_relevance > 0.0 and score < min_relevance:
            continue
        results.append(
            VectorIndexResult(
                file_path=file_path,
                content=content,
                score=score,
            )
        )

    return results
```

#### Additional helpers mirroring ChromaDB collection API

The REPL `db` command calls `collection.count()` and `collection.peek()`.
Rather than changing the REPL to call free functions, wrap the connection
in a thin adapter class:

```python
class FTSCollectionAdapter:
    """Adapter so the REPL `db` command works identically."""

    def __init__(self, conn: Any, db_path: Path):
        self._conn = conn
        self.name = f"fts_index ({db_path.name})"

    @property
    def conn(self):
        return self._conn

    def count(self) -> int:
        row = self._conn.execute("SELECT COUNT(*) FROM chunks").fetchone()
        return row[0] if row else 0

    def peek(self, limit: int = 5) -> Dict[str, Any]:
        rows = self._conn.execute(
            "SELECT id, file_path, content FROM chunks LIMIT ?",
            (limit,),
        ).fetchall()
        return {
            "ids": [r[0] for r in rows],
            "metadatas": [{"file_path": r[1]} for r in rows],
            "documents": [r[2] for r in rows],
        }
```

`initialize_index()` returns `FTSCollectionAdapter(conn, db_path)` so it
can be stored in `self.collection` exactly like the ChromaDB collection.

The free functions (`update_index_coarse`, etc.) accept either the adapter
or a raw connection. Inside each function, unwrap:

```python
def _get_conn(collection_or_conn: Any):
    if hasattr(collection_or_conn, 'conn'):
        return collection_or_conn.conn
    return collection_or_conn
```

#### Chunking

Reuse `ast_chunker` and `_chunk_file` from the existing codebase (import
them). No duplication.

#### Thread safety

`sqlite3.connect(..., check_same_thread=False)` + WAL mode.

Your indexing pipeline uses `DaemonThreadPoolExecutor` with up to 4 workers
writing concurrently. SQLite serializes writes internally when using WAL,
so this works without explicit locking — but writes may contend under heavy
load. This is acceptable because:
- FTS inserts are fast (no embedding computation).
- Batch sizes are small (5 files per batch).
- The 0.1s sleep between batches already throttles writes.

If contention becomes an issue, the 5-second default `busy_timeout` can be
increased:
```python
conn.execute("PRAGMA busy_timeout = 10000")
```

**Risk:** Medium — most code in the plan. Needs unit tests.

### Step 3 — Create a unified dispatch layer

**New file:** `model/vector_dispatch.py`

This is the facade that the rest of the codebase calls instead of
importing `vector_db` or `vector_db_fts` directly.

```python
"""Unified dispatch layer for vector/FTS search backends."""

from pathlib import Path
from typing import Any, Dict, List

from aye.model.models import VectorIndexResult
from aye.model.vector_backend import is_chroma_available


def initialize_index(root_path: Path) -> Any:
    if is_chroma_available():
        from aye.model import vector_db
        return vector_db.initialize_index(root_path)
    else:
        from aye.model import vector_db_fts
        return vector_db_fts.initialize_index(root_path)


def update_index_coarse(collection: Any, files_to_update: Dict[str, str]) -> None:
    if is_chroma_available():
        from aye.model import vector_db
        vector_db.update_index_coarse(collection, files_to_update)
    else:
        from aye.model import vector_db_fts
        vector_db_fts.update_index_coarse(collection, files_to_update)


def refine_file_in_index(collection: Any, file_path: str, content: str) -> None:
    if is_chroma_available():
        from aye.model import vector_db
        vector_db.refine_file_in_index(collection, file_path, content)
    else:
        from aye.model import vector_db_fts
        vector_db_fts.refine_file_in_index(collection, file_path, content)


def delete_from_index(collection: Any, deleted_files: List[str]) -> None:
    if is_chroma_available():
        from aye.model import vector_db
        vector_db.delete_from_index(collection, deleted_files)
    else:
        from aye.model import vector_db_fts
        vector_db_fts.delete_from_index(collection, deleted_files)


def query_index(
    collection: Any,
    query_text: str,
    n_results: int = 10,
    min_relevance: float = 0.0,
) -> List[VectorIndexResult]:
    if is_chroma_available():
        from aye.model import vector_db
        return vector_db.query_index(collection, query_text, n_results, min_relevance)
    else:
        from aye.model import vector_db_fts
        return vector_db_fts.query_index(collection, query_text, n_results, min_relevance)
```

All imports of `chromadb` and `vector_db` are **lazy** (inside `if` blocks).
On Python 3.14, the `chroma` branch is never entered.

**Risk:** Low. Pure dispatch, no logic.

### Step 6 — Conditional pip dependency

#### `pyproject.toml` (or `setup.cfg`)

```toml
[project]
dependencies = [
    # ... existing deps ...
    "chromadb>=0.4; python_version < '3.14'",
]
```

This means:
- On Python 3.10–3.13: `pip install aye-chat` pulls in `chromadb` as before.
- On Python 3.14: `chromadb` is **not installed**. `vector_backend.py`
  detects `ImportError` and selects the FTS backend.

#### Python version classifier

Add 3.14 to the supported versions:

```toml
[project]
classifiers = [
    "Programming Language :: Python :: 3.10",
    "Programming Language :: Python :: 3.11",
    "Programming Language :: Python :: 3.12",
    "Programming Language :: Python :: 3.13",
    "Programming Language :: Python :: 3.14",
]
```

And ensure you build/publish a universal wheel (you likely already do).

**Risk:** Low.

## FTS Quality Expectations

FTS5/BM25 is **lexical** search, not semantic. Practical implications:

| Query type | FTS quality | Notes |
|-----------|-------------|-------|
| Function/class name lookup | **Excellent** | Exact token match |
| Error message search | **Excellent** | Exact string fragments |
| "Where do we handle auth?" | **Good** | Matches "auth", "handle" tokens |
| "Refactor this to be cleaner" | **Poor** | No semantic understanding |
| Symbol search (`parse_config`) | **Excellent** | Tokenizer splits on `_` |

For a code-search RAG use case, FTS is surprisingly effective because:
- Most user queries contain identifiers or keywords from the code.
- The Porter stemmer handles common English variations.
- Code files contain function names, variable names, and comments that
  are highly lexically matchable.

This is a **good-enough** fallback, not a permanent replacement.

## Future: When ChromaDB Supports 3.14

Once `onnxruntime` ships 3.14 wheels:
1. Remove the `python_version < '3.14'` guard from `pyproject.toml`.
2. `vector_backend.py` will auto-detect Chroma and select it.
3. Users on 3.14 get semantic search automatically.
4. FTS backend remains as a fallback for edge cases.

No code changes needed — the dispatch layer handles it.
